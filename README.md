# 书源有效性检测工具

一个自动体检「阅读 3.0 / Legado」书源的工具。丢进书源文件，它会自动：

1. **按域名合并去重** —— 同一站的多个线路只留最完整的一条
2. **逐个真实检测** —— 搜索书名 → 打开目录 → 打开正文，三步全通才算有效
3. **记录耗时** —— 从发起搜索到拿到正文的毫秒数，写进书源字段 `zakaDelay`
4. **按快慢排序输出** —— 快的在前，慢的在后
5. **失败的也单独出一份** —— 完整字段的失败书源 + 精简清单 + 明细表，卡在哪一步一眼看到
6. **打包保存** —— 有效书源、失败书源、检测报告、汇总说明一起打包，可直接提交回仓库

全程在 GitHub Actions 上跑，不用自己有服务器。

---

## 一、三步上手

### 1. 把书源文件放进 `booksources/`

```
booksources/
├── 我的书源1.json
├── 我的书源2.json
└── 合集.txt          # 也行，只要是 JSON 数组格式
```

支持多文件、子目录、`.json` 和 `.txt`。会自动递归扫描，不用改任何代码。

### 2. 启动工作流

打开仓库的 **Actions** 页面 → 左侧选 **书源有效性检测** → 右侧 **Run workflow**。

参数一般不用动，直接点绿色的运行按钮。想快一点可以把「并发线程数」调到 64～96。

> 往 `booksources/` 里提交新文件时也会自动触发；另外每周一凌晨 3 点会自动体检一次。

### 3. 拿结果

跑完之后，在同一页面的底部 **Artifacts** 里下载 `书源检测结果`，或者直接看仓库里的 `dist/` 目录：

| 文件 | 内容 |
|---|---|
| `有效书源_N条.json` | 能用的书源，已按 `zakaDelay` 从快到慢排好 |
| `失败书源_N条.json` | **不能用的，保留全部原始规则字段**，加了失败诊断字段，可直接导入阅读器或拿去修 |
| `失败书源_精简_N条.json` | 失败源的精简清单，只有名称/地址/分组/原因/卡在哪一步，体积小，方便贴给人看 |
| `失败书源明细.csv` | 每条失败源的明细表：卡在哪一步、原因、详情、失败耗时、域名、地址 |
| `检测报告.csv` | 全部条目的详细数据：各阶段耗时、章节数、正文字数 |
| `检测汇总.md` | 总览：有效率、失败原因分布（按卡在哪一步归类）、失败明细前 30、最快 30 个 |
| `有效书源_打包.zip` | 上面全部文件的打包 |

`有效书源_N条.json` 就是最终成品，直接导入阅读 App 就能用。

## 二、本地跑（不依赖 GitHub）

```bash
pip install -r requirements.txt

# 全量检测
python check_booksources.py --src booksources --out dist

# 先测 50 条看看效果
python check_booksources.py --src booksources --limit 50 --workers 32
```

Windows 上也一样，装好 Python 3.9+ 即可。

## 三、参数说明

| 参数 | 默认 | 说明 |
|---|---|---|
| `--src` | `booksources` | 书源文件或目录，可以写多个：`--src a.json b.json dir/` |
| `--out` | `dist` | 输出目录 |
| `--workers` | 32 | 并发线程数。GitHub 上 48～96 都行，太大容易被站点限流 |
| `--timeout` | 12 | 单次请求超时秒数。慢站多的话可以调大 |
| `--min-content` | 200 | 正文最少字数，低于这个判为正文无效 |
| `--limit` | 0 | 只测前 N 条，调试用 |
| `--keywords` | 内置 | 搜索用的书名，逗号分隔。默认 `斗罗大陆,诡秘之主,三体,剑来,凡人修仙传` |
| `--no-merge` | 关 | 只按 URL 精确去重，不做域名合并 |
| `--resume` | 关 | 断点续跑，跳过已经测过的 |
| `--deadline-min` | 0 | 整体时间预算（分钟），到点就落盘收工，防止 Actions 超时被杀 |
| `--fail-lean` | 关 | 失败书源只输出精简字段（默认保留全部原始字段，这样能直接导入/拿去修） |

> **关键词选常用的**。生僻词容易搜不到，会被误判成失效；书源里如果自带 `checkKeyWord` 会优先用它的。

## 四、输出里的新字段

每条书源除了原有字段，会多出这几个（阅读 App 会忽略不认识的字段，不影响导入）：

| 字段 | 说明 |
|---|---|
| `zakaDelay` | **从发起搜索到拿到正文的总耗时（毫秒）**，越小越快 |
| `zakaCheck` | `ok` 有效 / `fail` 无效 |
| `zakaDomain` | 归一化后的域名（去掉 www 和协议） |
| `zakaAlias` | 同域名合并时被合并掉的其他书源名（有才出现） |
| `zakaAltUrls` | 合并掉的其他线路地址（有才出现） |
| `zakaBook` | 测试时搜到的书名 |
| `zakaChapters` | 解析到的章节数 |
| `zakaContentLen` | 抓到的正文字数 |
| `zakaReason` | 失败原因（仅失败源） |
| `zakaFailStep` | **卡在哪一步**：前置 / 搜索 / 目录 / 正文 / 规则 / 其它 |
| `zakaFailTime` | 失败前走到的耗时（毫秒），用于判断是慢死还是直接连不上 |

排序规则：有效的按 `zakaDelay` 从小到大；失败源另成一表，按卡住的步骤（前置 → 搜索 → 目录 → 正文）+ 原因归类。
`失败书源_N条.json` 里每条都保留了原书源的完整规则字段，所以它本身就是一个合法书源数组，导入阅读器能直接看到这些源（虽然大概率不能用），更方便的做法是拿它去逐条修规则。

## 五、判定标准（为什么会判失效）

一本书必须连续走通三步：

1. **搜索** —— 按书名搜出结果，且能解析出书籍链接
2. **目录** —— 打开书籍页 / 目录页，能解析出章节列表
3. **正文** —— 打开章节页，能取到正文且字数 ≥ `--min-content`

任何一步断了都判失效，并记下原因：

| 原因 | 含义 | 能救吗 |
|---|---|---|
| `搜索请求失败` | 域名解析不了 / 连不上 / 403 / 404 | 站点已死，救不了 |
| `搜索无结果` | 请求成功但搜不到书 | 可能网站改版了，也可能关键词太生僻 |
| `目录为空` | 目录规则匹配不到章节 | 网站改版，要更新规则 |
| `正文为空` / `正文过短` | 章节页拿不到正文 | 常见于需要登录/VIP 的站 |
| `规则依赖JS` | 规则里写了 `<js>` / `@js:` | 本工具不执行 JS，需要浏览器环境 |
| `无搜索地址` | 书源没有 `searchUrl` | 只能发现不能搜索的源 |
| `域名解析失败` | 本机 DNS 解析不了该域名 | 常见于国内域名 + 海外网络环境，换 Actions 跑通常正常 |

**有效率低很正常。** 网上流传的聚合书源里，三到五成是死站，还有一部分靠 JS 渲染。同一个源如果你在阅读 App 里能正常搜到、这里却判失效，八成是规则里有 JS 或者站点需要特殊 cookie —— 报告里的 `detail` 会写清楚卡在哪一步。

## 六、目录结构

```
booksource-checker/
├── check_booksources.py     # 主程序
├── merge_results.py         # 分片结果合并（Actions 用，本地一般不用）
├── requirements.txt
├── booksources/             # ← 书源文件放这里
├── dist/                    # ← 结果输出到这里
├── bscheck/
│   ├── rules.py             # 规则解析引擎（DefaultRule / CSS / XPath / JSONPath / 正则 / && ||）
│   ├── fetcher.py           # HTTP 层（编码识别、超时、代理、URL 归一）
│   ├── dedupe.py            # 加载 + 域名合并去重
│   └── checker.py           # 检测流水线（搜索 → 目录 → 正文）
└── .github/workflows/check.yml
```

## 七、常见问题

**Q：一次能跑多少条？会不会超时？**
实测 48 并发大约每分钟 100～150 条。GitHub Actions 单个任务上限 6 小时，够跑两万条左右。真跑不完就设 `--limit` 分批，或用 `--resume` 断点续跑。

**Q：为什么有的源在 App 里能用，这里判失效？**
常见三种：规则里用了 `<js>`（本工具不执行 JS）、站点要登录 cookie、站点对机房 IP 有限流。报告 `detail` 列会写明卡在哪一步，你可以在 App 里再确认一次。

**Q：域名合并会不会把不同线路误合并？**
按 host 归一（去 `www.`、去协议），同一 host 只留规则最完整的一条。被合并的名字和地址会写进 `zakaAlias` / `zakaAltUrls`，随时可查。不想合并就加 `--no-merge`。

**Q：结果会自动提交回仓库吗？**
默认会（只提交成品，不提交中间文件）。不想提交就把 `commit_result` 设成 `false`，只从 Artifacts 下载。

**Q：能不合并、只检测吗？**
可以，加 `--no-merge`。

## 八、失败书源怎么救（重写功能）

检测出来的失败书源，不用一个个手改。`fix_failed.py` 会按**卡在哪一步**对症重建规则，重建完必须真跑通「搜索→目录→正文」才算修好。

```bash
# 拿一份失败书源清单去重写
python fix_failed.py --src dist/失败书源_1434条.json --out dist_rewrite --workers 16
```

输出三样：

| 文件 | 内容 |
|---|---|
| `有效书源_重写_N条.json` | 救回来的，已按 `zakaDelay` 从快到慢排好，可直接导入阅读器 |
| `仍失败_M条.json` | 救不回来的，字段更新为本次检测结果，附卡在哪一步 |
| `修复报告.md` | 重写方式统计 + 仍失败原因分布 |

### 它会怎么救

| 卡在哪 | 重写动作 |
|---|---|
| 地址无效（域名后粘了「乃星」「-3」「##1」这类垃圾） | 截出合法域名重建地址 |
| 搜索请求失败 | 试 http/https 互换、换桌面 UA、抓首页搜索表单重建 searchUrl |
| 搜索无结果 | 多半是这个站没这本书：换热门书名重新验证，把能搜到的词写进 `checkKeyWord` |
| 搜索规则解析失败 | 用原搜索地址抓一页，按「重复的条目容器」重新生成 `bookList` |
| 目录为空 / 章节链接取不到 | 在书籍页按章节 URL 模式找章节组，重建 `chapterList / chapterName / chapterUrl` |
| 正文为空 / 过短 | 找文本量最大的正文容器，重建 `ruleContent` |
| 规则依赖 JS | 把带 JS 的那一段换成等价静态规则 |

### 两个前提要清楚

- **站点得还活着**。域名解析不了、返回 404、连不上的，规则再怎么写也救不回来——这类只能放弃。
- **本机 DNS 不给力时会误判**。报告里标「本地 DNS」的那批，站其实是好的，换网络或用 GitHub Actions 跑就正常。

### 在工作流里跑

Actions → 左侧 **失败书源重写** → 填失败书源路径（默认 `dist/失败书源_1434条.json`）→ Run workflow。
跑完结果在 Artifacts，也会提交回仓库 `dist_rewrite/`。

## 九、免责说明

本工具只做「发请求 + 解析页面」的连通性检测，不破解任何站点、不绕过登录和付费墙。请只检测你有权访问的书源，检测频率别开太高，避免给目标站点造成压力。
